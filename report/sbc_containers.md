## 요약

급식기의 AI 처리 장치인 **SBC(RK3566)** 안에서 돌아가는 소프트웨어를 **Docker 컨테이너 4개**로 나눕니다.

| 컨테이너 | 한 줄 역할 | 사용하는 장치 |
|---|---|---|
| **vision** | 카메라 영상으로 얼굴을 찾고 누구인지 알아냄 (NCNN) | 카메라, GPU |
| **controller** | 급여 여부를 판단하고 ESP32-S3에 명령, 섭취량 기록 | UART |
| **connect** | 서버와 통신 (기록 전송, 알림, 업데이트 수신) | Wi-Fi |
| **broker** | 컨테이너끼리 메시지를 전달하는 우체국 (로컬 MQTT) | – |

```
카메라 → [vision] ─인식 결과→ [broker] ─→ [controller] ─UART→ ESP32-S3 (모터·센서)
                                  │
                                  └──→ [connect] ─Wi-Fi→ 클라우드 서버
```

- **나누는 이유:** 하나가 멈춰도 나머지는 동작하고, 필요한 부분만 따로 업데이트할 수 있습니다.
- **핵심 효과:** 인터넷이 끊기거나 AI가 재시작되어도 **급여 제어는 멈추지 않습니다.**

## 1. 개요

### 1.1 목적

RK3566(SBC)에서 실행할 소프트웨어를 역할별 컨테이너로 나누는 방법과 그 이유를 정리합니다. ESP32-S3(MCU)는 운영체제가 없어 컨테이너를 쓸 수 없으므로 이 문서의 범위에서 제외합니다.

### 1.2 용어

| 용어 | 쉬운 설명 |
|---|---|
| **컨테이너** | 프로그램 하나를 실행에 필요한 라이브러리, 설정과 함께 포장한 상자. 상자끼리 서로 영향을 주지 않음 |
| **Docker** | 컨테이너를 만들고 실행하는 가장 널리 쓰이는 도구 |
| **이미지** | 컨테이너를 만드는 설계도 파일. 업데이트는 새 이미지로 바꾸는 방식으로 함 |
| **Docker Compose** | 여러 컨테이너를 설정 파일 하나로 한꺼번에 실행하고 관리하는 도구 |
| **MQTT** | 작은 메시지를 "주제(topic)"별로 주고받는 가벼운 통신 규칙 |
| **브로커 (broker)** | MQTT 메시지를 받아서 필요한 곳에 나눠 주는 중계 프로그램 |
| **볼륨 (volume)** | 컨테이너를 지우거나 새로 만들어도 데이터가 남도록 따로 둔 저장 공간 |

### 1.3 전제 조건

| 항목 | 내용 | 출처 |
|---|---|---|
| SBC | Rockchip RK3566 (ARM Cortex-A55 4코어, Mali-G52 GPU, Linux) | 하드웨어 부품 보고서 |
| MCU | ESP32-S3, RK3566과 UART로 연결 | 하드웨어 부품 보고서 |
| 추론 엔진 | NCNN (CPU + Vulkan GPU) | 추론 엔진 선정 보고서 |
| AI 모델 | YOLO11n-pose (얼굴 검출) + MobileFaceNet (개체 식별) | 모델 설계 보고서 |
| 서버 통신 | Wi-Fi + MQTT over TLS, AWS IoT Core | PRD |
| 필수 요구 | 인터넷이 끊겨도 급여 (오프라인 모드), OTA 업데이트 | PRD |

## 2. 왜 나누는가

### 2.1 한 덩어리로 만들 때의 문제

모든 기능을 프로그램 하나에 넣으면 다음 문제가 생깁니다.

| 문제 | 예시 |
|---|---|
| 하나가 죽으면 전부 멈춤 | AI 모델이 메모리 부족으로 멈추면 급여 제어와 서버 통신까지 같이 멈춤 |
| 일부만 바꾸기 어려움 | AI 모델만 새 버전으로 바꿔도 프로그램 전체를 다시 배포해야 함 |
| 라이브러리 충돌 | AI용 라이브러리와 통신용 라이브러리가 서로 다른 버전을 요구할 수 있음 |
| 원인 찾기 어려움 | 오류 기록이 한곳에 섞여서 어디서 문제가 났는지 알기 어려움 |

### 2.2 나누면 좋아지는 점

| 효과 | 이 제품에서 |
|---|---|
| **장애 격리** | vision이 재시작되는 동안에도 controller가 덮개를 닫고 스케줄 급여를 이어감 |
| **부분 업데이트** | 새 AI 모델은 vision 이미지만 교체. 급여 제어는 그대로 |
| **오프라인 동작** | 인터넷이 끊겨 connect가 서버에 못 붙어도, vision과 controller는 기기 안에서 계속 동작 |
| **자동 복구** | 멈춘 컨테이너만 Docker가 자동으로 다시 실행 |
| **같은 환경 재현** | 개발 PC와 실제 급식기에서 같은 이미지를 쓰므로 "내 PC에서는 됐는데" 문제가 줄어듦 |

## 3. 컨테이너 구성

### 3.1 vision: 카메라와 AI 인식

| 항목 | 내용 |
|---|---|
| 역할 | 카메라 영상을 받아 전처리하고, NCNN으로 얼굴 검출과 개체 식별을 실행 |
| 시작 조건 | controller가 "접근 감지(30cm 이내)"를 알리면 인식 시작, 떠나면 중지 |
| 입력 | 카메라 영상, 등록된 개체 특징 벡터 |
| 출력 | 인식 결과 (예: "초코, 유사도 0.91") |
| 주요 소프트웨어 | NCNN, OpenCV (전처리), 모델 파일 (.param / .bin) |
| 사용 장치 | 카메라, GPU (Vulkan) |
| 저장 데이터 | 등록된 개체 특징 벡터 (볼륨에 보관) |

### 3.2 controller: 급여 판단과 기기 제어

| 항목 | 내용 |
|---|---|
| 역할 | 인식 결과와 급여 스케줄로 급여 여부를 판단하고 ESP32-S3에 명령. 섭취량 기록 |
| 입력 | vision 인식 결과, ESP32-S3의 센서 값 (거리, 무게), 서버에서 온 급여 스케줄 |
| 출력 | ESP32-S3 명령 (예: "덮개 열기", "25g 토출"), 급여·섭취 기록 |
| 주요 소프트웨어 | 급여 판단 로직, 시리얼(UART) 통신, SQLite (기록 저장) |
| 사용 장치 | UART (ESP32-S3 연결) |
| 저장 데이터 | 급여 스케줄, 섭취 기록 (볼륨에 보관, 오프라인일 때도 기록 유지) |
| 특징 | **가장 중요한 컨테이너.** 다른 컨테이너가 멈춰도 이 컨테이너만 살아 있으면 스케줄 급여가 가능함 |

### 3.3 connect: 서버 통신

| 항목 | 내용 |
|---|---|
| 역할 | 기기와 클라우드 서버 사이의 모든 통신 담당 |
| 보내는 것 | 섭취 기록, 기기 상태, 오류 알림 |
| 받는 것 | 급여 스케줄 변경, 새 개체 등록 사진, 새 AI 모델·펌웨어 (OTA) |
| 주요 소프트웨어 | MQTT 클라이언트 (TLS 인증서 포함), 업데이트 다운로드 |
| 사용 장치 | Wi-Fi (네트워크) |
| 특징 | 인터넷이 끊긴 동안 쌓인 기록은 연결이 돌아오면 한꺼번에 전송 |

### 3.4 broker: 기기 안 메시지 우체국

| 항목 | 내용 |
|---|---|
| 역할 | 기기 안 컨테이너끼리 메시지를 전달 |
| 주요 소프트웨어 | Mosquitto (가벼운 MQTT 브로커) |
| 따로 두는 이유 | broker를 connect 안에 넣으면, connect가 멈출 때 vision과 controller 사이 연락도 끊김. 그래서 독립된 컨테이너로 둠 |
| 외부 접근 | 기기 안에서만 열고 외부 네트워크에는 열지 않음 |

### 3.5 MCU와의 역할 구분

| 위치 | 담당 |
|---|---|
| RK3566 컨테이너 | 판단: 누구인지, 줄지 말지, 얼마나 줄지, 기록과 통신 |
| ESP32-S3 (MCU) | 실행: 모터 회전, 덮개 개폐, 센서 측정 (실시간 제어) |

## 4. 컨테이너끼리 주고받는 메시지

broker를 거쳐 주제(topic)별로 메시지를 주고받습니다.

| 주제 (topic) | 보내는 곳 → 받는 곳 | 내용 예시 |
|---|---|---|
| `device/approach` | controller → vision | `{"state": "near", "distance_cm": 27}` |
| `vision/result` | vision → controller | `{"pet": "choco", "similarity": 0.91}` |
| `feeder/event` | controller → connect | `{"pet": "choco", "dispensed_g": 24.8, "eaten_g": 23.1}` |
| `feeder/schedule` | connect → controller | `{"pet": "choco", "time": "07:30", "amount_g": 45}` |
| `vision/enroll` | connect → vision | 새 개체 등록 사진 (3~5장) |
| `system/update` | connect → 각 컨테이너 | 새 모델·이미지 버전 알림 |
| `system/health` | 각 컨테이너 → controller | 상태 확인 신호 (살아 있음) |

## 5. 장치 연결

컨테이너는 기본적으로 기기의 장치에 접근할 수 없습니다. 필요한 장치만 골라서 연결해 줍니다.

| 컨테이너 | 연결할 장치 | 리눅스 장치 경로 (예시) |
|---|---|---|
| vision | 카메라 | `/dev/video0` |
| vision | GPU (Vulkan) | `/dev/dri` |
| controller | ESP32-S3와 연결된 UART | `/dev/ttyS3` |
| connect | 네트워크 | 장치 연결 없음 (네트워크만 사용) |

장치 경로는 보드와 운영체제 설정에 따라 달라지므로 실제 보드에서 확인해야 합니다. 필요한 장치만 연결하면, 한 컨테이너에 문제가 생겨도 다른 장치를 잘못 건드리지 않습니다.

## 6. 동작 흐름

반려동물 "초코"가 급식기에 다가왔을 때의 순서입니다.

| 순서 | 컨테이너 | 하는 일 |
|---|---|---|
| ① | controller | ESP32-S3로부터 "30cm 이내 접근" 신호를 받음 → `device/approach` 발행 |
| ② | vision | 카메라를 켜고 얼굴 인식 → `vision/result`로 "초코, 0.91" 발행 |
| ③ | controller | 초코의 급여 시간인지 확인 → ESP32-S3에 "덮개 열기", "25g 토출" 명령 |
| ④ | controller | 초코가 떠나면 남은 무게로 섭취량 계산 → 기록 저장 → `feeder/event` 발행 |
| ⑤ | connect | 섭취 기록을 서버로 전송 → 보호자 앱에 알림 |

## 7. 문제 상황별 동작

| 상황 | 영향 받는 컨테이너 | 급식기 동작 |
|---|---|---|
| 인터넷 끊김 | connect | 기기 안 인식과 급여는 정상. 기록은 쌓아 두었다가 연결되면 전송 |
| AI 인식 오류로 vision 재시작 | vision | controller가 덮개를 닫은 상태로 유지. 재시작 후 바로 인식 재개 |
| 새 AI 모델 업데이트 | vision | vision 이미지만 교체. 교체 중에는 급여를 보류하고 이후 재개 |
| broker 재시작 | broker | 몇 초간 메시지 지연. controller는 저장된 스케줄로 판단 가능 |
| controller 오류 | controller | Docker가 자동 재시작. ESP32-S3는 명령이 없으면 덮개를 닫고 모터를 멈춤 (안전 상태) |

## 8. 자원 사용 계획

RK3566 보드는 보통 RAM 2~4GB를 씁니다. 컨테이너별 예상 사용량은 다음과 같습니다.

| 컨테이너 | 예상 메모리 | 예상 CPU 사용 |
|---|---|---|
| vision | 약 300~500 MB | 인식 중 높음, 대기 중 거의 없음 |
| controller | 약 30~60 MB | 낮음 |
| connect | 약 30~60 MB | 낮음 |
| broker | 약 5~10 MB | 매우 낮음 |
| Docker 엔진 | 약 100 MB | 낮음 |
| **합계** | **약 0.5~0.7 GB** | |

위 값은 비슷한 구성의 일반적인 사용량을 바탕으로 한 예상치이며, 실제 보드에서 측정해야 합니다. RAM 2GB 보드에서도 여유가 있을 것으로 예상합니다.

**컨테이너별 사용량 제한:** vision이 메모리를 너무 많이 쓰더라도 controller가 영향을 받지 않도록 컨테이너마다 메모리 상한을 둡니다.

## 9. 실행 설정 예시

Docker Compose 설정 파일 하나로 네 컨테이너를 함께 실행합니다.

```yaml
services:
  broker:
    image: eclipse-mosquitto:2
    restart: always
    ports: ["127.0.0.1:1883:1883"]   # 기기 안에서만 접속

  vision:
    image: pawfeeder/vision:1.0
    restart: always
    devices:
      - /dev/video0                   # 카메라
      - /dev/dri                      # GPU (Vulkan)
    volumes:
      - pets:/data/pets               # 등록된 개체 특징 벡터
    mem_limit: 700m
    depends_on: [broker]

  controller:
    image: pawfeeder/controller:1.0
    restart: always
    devices:
      - /dev/ttyS3                    # ESP32-S3 UART
    volumes:
      - logs:/data/logs               # 급여 스케줄, 섭취 기록
    mem_limit: 128m
    depends_on: [broker]

  connect:
    image: pawfeeder/connect:1.0
    restart: always
    volumes:
      - certs:/certs:ro               # 서버 인증서 (읽기 전용)
    mem_limit: 128m
    depends_on: [broker]

volumes:
  pets:
  logs:
  certs:
```

- `restart: always`: 컨테이너가 멈추면 자동으로 다시 실행합니다.
- `devices`: 필요한 장치만 연결합니다.
- `volumes`: 컨테이너를 새 버전으로 바꿔도 등록 정보와 기록이 남습니다.
- `mem_limit`: 컨테이너별 메모리 상한입니다.

## 10. 고려사항

| 항목 | 내용 | 대응 |
|---|---|---|
| 저장 공간 | 이미지마다 용량을 차지함 | ARM용 가벼운 기본 이미지 사용, 쓰지 않는 옛 이미지 정리 |
| 부팅 시간 | Docker와 컨테이너가 켜지는 데 시간이 걸림 | controller를 먼저 띄우고, 전원이 켜지면 바로 스케줄 급여가 가능하게 함 |
| GPU 사용 | 컨테이너 안에서 Vulkan을 쓰려면 GPU 드라이버 연결이 필요 | 실제 보드에서 컨테이너 안 NCNN GPU 동작을 먼저 확인 |
| 보안 | 서버 인증서와 개체 정보 보호 | 인증서는 읽기 전용 연결, broker는 기기 밖에 열지 않음 |
| 업데이트 실패 | 새 이미지가 제대로 동작하지 않을 수 있음 | 이전 버전 이미지를 남겨 두고 문제가 생기면 되돌림 |
| 영상 보호 | 반려동물 영상이 밖으로 나가면 안 됨 | 영상은 vision 안에서만 처리하고, 다른 컨테이너에는 인식 결과만 전달 |

## 11. 결론

1. RK3566(SBC) 소프트웨어를 **vision, controller, connect, broker 4개 컨테이너**로 나눕니다.
2. 이렇게 나누면 **하나가 멈춰도 급여는 계속되고**, AI 모델처럼 **필요한 부분만 따로 업데이트**할 수 있습니다.
3. 가장 중요한 급여 판단은 controller가 맡고, 인터넷이나 AI 쪽 문제가 있어도 controller만 살아 있으면 스케줄 급여가 가능하도록 설계합니다.
4. 컨테이너에는 카메라, GPU, UART 등 **필요한 장치만 연결**하고, 영상은 vision 밖으로 내보내지 않습니다.
5. 전체 예상 메모리는 약 0.5~0.7GB입니다. 실제 보드에서 메모리 사용량과 컨테이너 안 GPU 동작을 확인해야 합니다.
